# 派发工作给 Codex CLI

本技能只管**怎么派、怎么看进度、怎么收结果**，不规定 Codex 是什么角色。角色由调用方决定：需要按项目分工工作时加 `--role`（例如 `dual-role-workflow` 派工程任务时加 `--role engineering`）；不加就是一项普通工作。

下文的 `<技能目录>` 指本文件所在目录的绝对路径。目录里：

- `codex-task.mjs`：派发脚本，在**目标仓库根目录**运行。只用 Node 自带模块，不需要安装依赖；`lib/`、`adapters/` 是它的组成部分，不要单独挪动。
- `codex-watch.cmd [仓库目录]`（Windows）：用户想随时手动打开进度窗口时运行它，显示该仓库最新一个任务的进度。

## 用法

```
node "<技能目录>/codex-task.mjs" <任务说明文件 | "任务文字"> ["补充说明"] [选项]
```

- 脚本以**当前工作目录**作为仓库根目录，运行前先切到仓库根目录。
- 第一个参数是存在的文件 → 当作任务说明，让 Codex 完成其中全部内容并验证、提交、汇报；否则当作直接给 Codex 的任务文字。
- 仓库根目录有 `AGENTS.md` 时，总是让 Codex 先读它。

| 选项 | 作用 |
|---|---|
| `--role <角色>` | 开头告诉 Codex"你在本项目中的角色是「xxx」"，并让它读 `docs/roles/<角色>.md`（角色名取自该文档第一个 `# 角色：xxx` 标题）。也可以直接给角色文档路径。不给就不提角色 |
| `--name <记录名>` | 记录文件名。任务说明默认用文件名，任务文字默认 `task-<时间>`。不能含路径符号和 `< > : " \| ? *` |
| `--sandbox <沙箱>` | 本次任务的沙箱。只读的调研、排查类工作用 `read-only` |
| `--model` / `--effort` / `--tier` | 本次任务的模型、推理强度、服务档位。一般不用给，见下面的"默认配置" |
| `--watch-window <auto\|always\|never>` | 本次是否弹出只读进度窗口 |

**不确定参数对不对**时，先在前台加环境变量 `CODEX_DRY_RUN=1` 跑一次：只打印实际记录名和将发给 Codex 的指令，不运行、不写任何文件。

### 记录文件

都在仓库的 `.codex-runs/` 下：`<记录名>.md`（最终汇报）、`<记录名>.progress.log`（给人看的精简进度）、`<记录名>.events.jsonl`（结构化事件，监控软件读它）、`<记录名>.log`（Codex 原始输出，排查用）。

**记录名已存在时自动加序号**（`-2`、`-3`……），旧任务的记录不会被覆盖。所以实际记录名可能和你给的不同：脚本开始时会在输出里打印实际的记录名和进度文件路径，以它为准。

### 默认配置

模型、推理强度、档位、沙箱、是否弹窗的默认值放在共享配置 `config.json` 里（Windows 在 `%APPDATA%\codex-dispatch\`，其他平台在 `~/.config/codex-dispatch/`）。

- 取值优先级：命令行选项 > 环境变量（`CODEX_MODEL`、`CODEX_EFFORT`、`CODEX_TIER`、`CODEX_SANDBOX`，`CODEX_NO_WATCH=1` 不弹窗）> `config.json` > 内置默认。
- 内置默认：模型、强度、档位都**跟随 Codex 自己的配置**（不传参数）；沙箱 `workspace-write`；窗口 `auto`。
- 查看当前默认值和来源：`node "<技能目录>/codex-task.mjs" --config`。修改：`--config model=<模型> effort=<强度> tier=<档位>`，值写 `-` 表示改回跟随 Codex。用户说"不用设"时运行 `--config init`，只建一份全部跟随 Codex 的配置，以后不再提示。
- 装了监控软件的话，用户也可以在软件的设置页里改。
- 派发时只为**这一次任务**决定参数（例如调研用 `--sandbox read-only`）。不要为了省事改用户的默认配置；要改默认值先问用户。

**首次使用**：脚本输出或进度开头出现 `配置：未找到 config.json…`，说明用户还没设过默认值。任务照常执行，不要停下来问；等这次任务结束、向用户汇报时顺带问一次：要不要设置派发的默认模型、推理强度和档位？不设就一直跟随 Codex 自己的配置。按用户的回答运行上面的 `--config` 命令。出现 `配置：config.json 无法读取…` 时，把原因转告用户。

### 监控软件

装了监控软件（DispatchDock）并开着时，所有派出的任务都在软件里统一查看、停止和验收，不再弹只读窗口；软件没开时自动退回只读窗口。两边都不影响任务本身。

如果用户在软件里打开了**托管**，任务由软件启动：关掉当前会话也不会中断任务，派发命令照常等到任务结束才退出。脚本输出会说明这次是否托管。托管的任务要停止，在软件里停。

## 步骤

1. **准备任务**。较大的工作写成任务说明文件：目标、范围、允许改动的文件、不做什么、验收标准、汇报要回答的问题；一次一个。小的一次性工作可以直接给任务文字。
2. **任务说明先提交**（只 `git add` 具体文件），让 Codex 从干净的基线开始。确认 `.codex-runs/` 在 `.gitignore` 里，不在就提醒用户或按项目约定加上。
<!-- host:dispatch -->
3. **后台派发**：用 Bash 工具，设 `run_in_background: true`，命令先切到仓库根目录再运行脚本，例如：
   ```bash
   cd "<仓库根目录>" && node "<技能目录>/codex-task.mjs" docs/specs/012-xxx.md --role engineering
   ```
   派出后读一下这条后台命令的输出，拿到实际记录名。
<!-- /host:dispatch -->
4. **告诉用户**任务已派出、记录名是什么、在哪里看进度：开着监控软件就在软件里看；否则 Windows 上会弹出标题为"Codex <记录名>（只看）"的窗口，也可以运行 `codex-watch.cmd` 手动打开。进度最后出现"=== Codex 结束：exit=0 …"就是做完了。给粗略的用时预期（小改动约 5 分钟，中等任务 10～30 分钟，大块工作可能一小时以上），不做精确承诺。
<!-- host:wait -->
5. **等待时**不要编辑 Codex 可能在改的文件，避免它 `git add` 时把你的半成品一起提交。可以做不冲突的事。后台命令结束时你会自动收到通知，**不要用 sleep 循环轮询**；用户问进度时用 Read 读 `progress.log` 的末尾几十行。
<!-- /host:wait -->
6. **结束后审查**：读 `.codex-runs/<记录名>.md` 汇报，有提交就看 `git log` / `git show --stat` 和关键 diff，自己再跑一遍项目的验证命令。汇报里的 TODO、偏离说明、已知问题逐条处理或转告用户。
7. **向用户汇报**用用户的语言、说白话：做了什么、验证结果、问题和下一步。

## 已知坑

<!-- host:interrupt -->
- **关闭 Claude Code 或结束当前会话，可能连带中断 Codex**（它是后台命令的子进程）。在会话内部让它脱离父进程的办法都不可靠；需要关掉会话也不中断，就让用户在监控软件里打开托管。中断了就重新派发，在补充说明里写明"上次中断，工作区里未提交的文件是上次写的，核对后继续"。
- 要主动停掉本会话派出的、没有托管的任务，用 TaskStop 停对应的后台命令。
<!-- /host:interrupt -->
- 同一任务不要同时跑两份：记录名会自动错开，但两份 Codex 会抢同一个工作区。重新派发前先确认旧任务已经结束（看监控软件，或看进度文件末尾有没有结束行；Windows 上也可以查进程：`Get-CimInstance Win32_Process | Where-Object { $_.CommandLine -match 'codex-task.mjs' }`）。
- 找不到 Codex 时脚本会报错退出：确认 `codex --version` 能运行。用 pnpm、scoop 等非标准方式安装的，在 `config.json` 的 `agents.codex.path` 里写 Codex 的绝对路径。
- Codex 升级后事件格式可能变化，表现为进度里只剩"说："或者出现很多原始文本行。原始输出都在 `.log` 里；把现象告诉用户，转换规则在 `adapters/codex.mjs`。
- Windows PowerShell 5 的 `Set-Content -Encoding UTF8` 和 `Out-File` 会写 BOM；给 Codex 准备的文件用编辑工具写。
