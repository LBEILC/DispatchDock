# 双角色协作

## 为什么这样分

判断和品味贵，执行量大。让用户指定的模型只做**需要判断的事**，把**能写清楚要求的执行工作**全部交给 Codex。设计负责人的 token 应该主要花在：和用户讨论、做决定、写清楚任务说明、看验收产物；但审美产物（含交互原型）要自己做出来，交互多的应用，原型就是产品的界面代码。

## 分工

| 角色 | 由谁担任 | 负责 |
|---|---|---|
| **设计负责人** | 当前对话的模型（就是你） | 方向与重大决策、审美（视觉、文案、节奏、手感、信息结构、"什么不该出现"）、和用户对话、写设计文档与任务说明、派发、验收、最终把关 |
| **工程负责人** | Codex CLI（用 `codex-dispatch` 技能加 `--role engineering` 派发） | 一切能说清要求、能客观验收的执行工作：写代码、搭脚手架、接数据、按参照实现交互少的界面、搭渲染 / 剪辑 / 构建管线、批量处理素材、给共享核心（会被反复调用、坏了影响全局的代码）写测试、调研与排查、性能优化、移植、修 bug。不做审美和方向取舍，遇到就留 `TODO(design)` |

**凡是用户直接感受到的东西（视觉、交互、动效、文案），设计负责人的定稿必须是能看、能点的产物**（界面稿、可交互原型、样片、定稿文案），不能只是文字。文字只用来记录"为什么"。只交文字要求时，Codex 会把文字没说到的地方自己填上，验收断言照样全过，手感差要等用户亲手用了才发现。

**交不交给 Codex，看两件事：描述是否明显比实现短，结果能否客观验收。** 两个都满足就派出去，否则自己做。用户明确要交给 Codex 的，直接派。动效和交互的时序看起来能用几个数字说清，但手感要看了、点了才知道，一律算"不能客观验收"，不派给 Codex。

- **派给 Codex**：有现成参照、能自动比对的（"和参考截图逐像素一致"、"照这份设计令牌实现"、"移植到另一个引擎"）；量大但照套路做的（一批同结构的页面 / 组件、数据接线、点击区域、脚本和管线）；一句话能说清的（"照现有卡片样式再做一张，字段是 A、B、C"）；以及所有纯工程工作。
- **设计负责人自己做**：审美还在摸索、要边看边调的表现层（动效手感、构图、节奏、元素怎么堆怎么晃）——把它写成精确到能照做的说明，本质上已经是在写代码，再加上来回审查和返工，比自己写一版、看一眼、改几个数更费 token 也更慢，效果还隔一层；以及改动很小、写说明比直接改还费的。
- **混合**：审美部分自己写，配套的数据、状态和要交的截图 / 渲染交给 Codex。审美定稿后，大批量复制同一套风格（更多页面、更多镜头、另一个平台）再交给 Codex，用定稿作参照验收。

核心原则：**角色写在文档里，不写在"你是哪个模型"里。** `AGENTS.md` 会被多数工具读到（Codex、Cursor、Devin……），所以它只放共同规则；各角色职责放在 `docs/roles/<角色>.md`。开工时明确告诉对方"你的角色是 X"，对方去读对应的角色文档。

## 不同类型工作里的分工示例

| 类型 | 设计负责人决定 | 交给 Codex 执行 |
|---|---|---|
| 游戏 | 玩法方向、数值取舍、美术风格、手感与反馈编排、文案；摸索期的表现层自己写 | 规则与状态、存档、输入、资源管线、测试、性能、按定稿画面移植到引擎 |
| 网页 / 应用 | 信息结构、视觉风格与设计令牌（颜色 / 字号 / 间距）、文案、什么不该出现；交互多的，整个界面层自己写在产品代码里（见下）；定共享的类型和命令定义 | 数据、命令和后端，照设计负责人定好的类型和命令定义实现；交互少的页面按定稿照样复制；响应式、可访问性检查、构建部署、测试、性能 |
| 视频 | 选题与脚本、分镜与节奏、镜头取舍、画面风格、字幕与配乐的取向；样片的节奏自己调 | 素材整理与转码、剪辑工程（FFmpeg / Remotion / 剪辑脚本）按分镜拼接、字幕生成与对齐、渲染与导出、批量出图、质量检查 |
| 文档 / 演示 | 结构与论点、语气、版式风格 | 排版实现、图表生成、格式转换、校对脚本、链接检查 |

**交互多的应用，界面层归设计负责人。** 先做 HTML 原型、再让 Codex 在产品里重写，每重写一遍都走样，同一套界面最后要做三遍（原型 → Codex 实现 → 设计负责人重写进产品）。所以原型直接写在产品的界面代码里，接假数据层，在浏览器的整体预览里迭代、给用户看；Codex 只做数据、命令和后端。两边以共享的类型和命令定义对接：先由设计负责人定接口，再写任务说明交给 Codex。

每个项目都要有**验收产物**，让设计负责人不用读全部代码就能判断结果：以截图、渲染短片、试听文件、可点的预览为主，在任务说明里写明要哪几样，由 Codex 随任务交出，不另建测试体系。一次性的生产任务不新写测试脚本。

接口两头的测试要对得上：本地的假服务、假数据层要复刻真实服务的校验规则（字段、长度、取值），否则问题要到真实环境才暴露。界面要的新数据，先由设计负责人在假数据层里写出来，并把接口写进任务说明；Codex 改真接口时同步更新假服务和假数据层，保证预览和产品一致。涉及收费或账号的接口，约定发版前做一次小额实测，清单和预算先给用户确认。

## 在一个项目里建立分工（`setup`）

先看项目现有的 `AGENTS.md`、`CLAUDE.md`、`.cursor/rules`、README 等，已有约定就在它基础上改，不推倒重来。和用户确认项目类型、技术栈、哪些产物代表"审美"（归设计）、哪些是"工程"（归 Codex）。然后建立三份文档，内容按项目实际情况写：

1. **`AGENTS.md`（共同规则）**
   - 项目一句话介绍、技术栈。
   - 角色表：角色名、负责什么、角色文档路径。
   - 明确写："开工前你会被告知自己的角色，然后读对应的角色文档；不要因为自己是哪个模型就推断角色；没被告知时先问用户。"
   - 共同规则：文件归属、只 `git add` 具体文件、提交信息格式（工程提交加 `[工程]` 前缀）、验证命令、不做无关改动、代码风格、平台注意事项、和用户交流用什么语言。
   - 文件归属表：设计文档、任务说明、风格 / 参数 / 文案类文件归设计（交互多的应用连界面代码一起）；其余代码、脚本、配置、测试归工程。
   - 文档地图：设计文档、任务说明目录、角色文档。
2. **`docs/roles/design.md`（设计负责人）**：负责什么、哪些文件自己动手（通常是摸索期的表现层、交互原型、风格参数、文案；交互多的应用是整个界面层）、交给工程的是什么、工作流程、验收手段、风格约定。另写一节"验收怎么写"：断言只守关键流程的最终状态、数据安全和权限边界，而且只验证这次改动真可能弄坏的；已交付的旧成果不做回归，共享代码改了抽一个跑通即可；视觉、动效和声音以目测、试听为准，不写断言，也不做逐像素、逐样本比对，除非改的就是确定性或渲染核心本身；本机只跑和改动相关的测试分类，全套交给 CI。
3. **`docs/roles/engineering.md`（工程负责人）**：第一行标题写 `# 角色：工程负责人`（派发脚本从这里取角色名）；"只做工程"；硬规则（不做审美 / 交互 / 方向取舍并留 `TODO(design)`、**照参照实现时只用已有的风格词汇**——颜色、字号、间距、组件、素材只从风格文件和现有实现里取，参照没覆盖的情况留 `TODO(design)` 而不是挑个差不多的，交互和动效的时长、曲线、先后顺序以原型为准，新美术素材归设计负责人、只用明显占位、遵守文件归属、按任务说明范围做、依赖需说明、不做无关改动）；完成标准（验证、提交；本机只跑和改动相关的测试分类，全套交给 CI，没有 CI 时只在改了共享核心时最后跑一次；只做任务说明「验收」里列出的验证，不自行增加防御性检查、回归、比对或重复试验，觉得有必要的写进汇报）；汇报格式（完成了什么 / 改动的文件 / TODO(design) 清单 / **推断清单**：说明和参照都没写明、靠自己推断的地方，哪怕觉得理所当然也要列 / 偏离说明 / 已知问题）。

   风险提示：工程负责人最容易出问题的不是明知故犯，而是**没意识到自己在做审美决定**（"调色板里有这个颜色就用了"、"放不下就缩小字号"）。"只用已有词汇"和"推断清单"就是为了把这类隐性决定暴露出来。

然后准备：设计文档（如 `docs/design.md`）、任务说明目录（如 `docs/specs/`，文件按 `NNN-简述.md` 编号）。确认 `.codex-runs/` 在 `.gitignore` 里。建好后提交，用用户的语言告诉用户分工和用法。

## 作为设计负责人干活

1. 读 `AGENTS.md`、`docs/roles/design.md`、设计文档。
2. **重大决策先问用户**，给出选项和你的建议；拍板后写进设计文档。
3. 按上面的判断标准，能说清、能客观验收的执行工作写成任务说明：目标、范围、允许改动的文件、不做什么、参数与参照、验收标准（包括要产出的验收产物）、汇报要回答的问题。一次一个。原型大改过的部分写"以原型（或现有实现）为准重写"：只列差别的话，没列到的地方 Codex 会保留旧组件打补丁。范围写死，不留"顺手打磨"这类开放项。要边看边调的审美部分自己做，做完看一眼产物就提交，不跑测试。
4. 提交任务说明后用 `codex-dispatch` 派发，**必须加 `--role engineering`**（codex-dispatch 本身不带角色）。项目自带派发脚本且已固定角色时用项目的。等待期间不碰 Codex 可能在改的文件。
5. 验收：先看汇报、**推断清单**和验收产物（截图 / 渲染），推断清单里涉及审美的逐条对照验收产物确认，再抽查关键 diff；不要逐行读全部代码。交互和动效要把实现和原型并排对照，不能只看截图和断言。处理 `TODO(design)` 和不满意的推断：做决定，写进下一个任务说明，或自己做最后的审美微调。

6. 用用户的语言、白话向用户汇报：做了什么、效果如何、问题、下一步、需要用户定的事。

## 多个设计负责人同时干活

同时开了不止一个设计负责人（比如不同工具里的两个会话）时，共用一个目录和分支会互相踩：一方切分支，另一方的提交落到错的分支；一方改共享核心，弄坏另一方的代码；交接靠用户来回复制粘贴，容易走样。所以：

- 每个设计负责人一个独立目录（或 git worktree）和自己的分支。
- 开工前划清文件归属，写进交接文档；共享核心只归一方，另一方要改就写进交接请对方改。
- 交接写成仓库里的文件（汇报或交接文档），不靠用户转述。
- 提交前先看当前分支，推送后核对远端。

## 被告知担任其他角色时

读 `AGENTS.md` 和对应的 `docs/roles/<角色>.md`，按那份文档工作；不要越权做另一个角色的决定。
